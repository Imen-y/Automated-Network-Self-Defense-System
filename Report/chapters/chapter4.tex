\chapter{Développement de la notification et de la réponse automatisée}

\section{Introduction}

Après le développement et la validation du moteur de détection SSH présenté dans le chapitre précédent, l'étape suivante du projet Automated Network Self-Defense System (ANSDS) consiste à mettre en place les premiers mécanismes de réponse aux événements de sécurité détectés.

La simple détection d'une attaque ne constitue pas une réponse suffisante face aux menaces actuelles. Un système de sécurité efficace doit être capable de transmettre rapidement les informations relatives à l'incident afin de réduire le temps de réaction de l'administrateur, puis d'appliquer automatiquement une mesure de protection lorsque cela est nécessaire.

Dans cette phase, deux mécanismes complémentaires sont développés. Le premier est un système de notification basé sur Telegram permettant d'informer automatiquement l'administrateur lorsqu'un comportement suspect est détecté. Le second repose sur Netmiko et permet d'automatiser les interactions avec le routeur Cisco afin d'appliquer dynamiquement une ACL de blocage.

Afin de conserver une architecture logicielle modulaire, les différents composants sont développés séparément puis intégrés progressivement au moteur de détection développé avec Scapy. Cette séparation facilite la maintenance, la réutilisation du code et l'évolution future du système.

Dans ce chapitre, nous présentons successivement le développement du système de notification Telegram, son intégration avec le moteur de détection, la mise en place de l'automatisation Cisco avec Netmiko, la création et la suppression dynamique des ACL, la gestion des exceptions ainsi que les validations expérimentales réalisées.

\section{Objectifs du chapitre}

Cette phase constitue une étape importante dans l'évolution du système ANSDS, puisqu'elle permet de passer d'un système capable uniquement de détecter une activité suspecte à un système capable également de notifier l'administrateur et d'appliquer automatiquement une mesure de protection.

Les objectifs principaux sont les suivants :

\begin{itemize}
    \item créer un bot Telegram destiné à recevoir les alertes de sécurité ;
    \item développer un module Python réutilisable permettant d'envoyer automatiquement des notifications ;
    \item intégrer ce module au moteur de détection SSH développé avec Scapy ;
    \item construire un message d'alerte contenant les informations essentielles relatives à l'attaque détectée ;
    \item transmettre automatiquement une notification dès que le seuil de détection est atteint ;
    \item préparer le routeur Cisco à l'automatisation distante ;
    \item installer et configurer la bibliothèque Netmiko ;
    \item développer un module Python dédié à la gestion des ACL Cisco ;
    \item appliquer dynamiquement une ACL permettant de bloquer une adresse IP identifiée comme malveillante ;
    \item supprimer automatiquement l'ACL après expiration de la durée de blocage ;
    \item gérer les erreurs pouvant survenir lors des communications avec le routeur ;
    \item intégrer l'ensemble des composants dans une chaîne de réponse automatisée ;
    \item valider expérimentalement le fonctionnement de chaque fonctionnalité.
\end{itemize}

\section{Développement du système de notification Telegram}

\subsection{Présentation de Telegram Bot API}

Telegram est une plateforme de messagerie instantanée proposant une interface de programmation appelée Telegram Bot API. Cette interface permet à des applications externes d'interagir automatiquement avec le service Telegram sans intervention humaine \cite{telegram_bot_api}.

Le principe repose sur la création d'un bot, c'est-à-dire un compte spécial administré par une application. Contrairement à un utilisateur classique, un bot peut recevoir des commandes, envoyer des messages, transmettre des fichiers et communiquer automatiquement avec les utilisateurs autorisés \cite{telegram_bot_api}.

L'accès à Telegram Bot API repose sur un jeton d'authentification (\textit{Bot Token}) généré lors de la création du bot. Ce jeton identifie de manière unique l'application et autorise l'envoi de requêtes vers les serveurs Telegram.

Chaque conversation Telegram possède également un identifiant numérique (\textit{Chat ID}) permettant de spécifier précisément le destinataire des notifications. L'association du Bot Token et du Chat ID permet ainsi au système de transmettre automatiquement les alertes de sécurité à l'administrateur.

Dans le cadre du projet ANSDS, Telegram est utilisé exclusivement comme canal de notification. Les informations produites par le moteur de détection sont transmises au bot afin d'informer immédiatement l'administrateur d'une activité suspecte observée sur le réseau.

\subsection{Création du Bot Telegram}

La première étape du développement consiste à créer un bot Telegram dédié aux notifications de sécurité.

Telegram met à disposition un service officiel nommé BotFather permettant de créer et d'administrer les bots. Après avoir lancé la commande \texttt{/newbot}, l'utilisateur choisit un nom d'affichage ainsi qu'un nom d'utilisateur unique se terminant obligatoirement par le suffixe \texttt{bot}.

Une fois la création terminée, BotFather génère automatiquement le Bot Token nécessaire à l'authentification auprès de Telegram Bot API \cite{telegram_bot_api}.

\subsection{Développement du module de notification}

Une fois les paramètres d'authentification obtenus, l'étape suivante consiste à développer un module Python capable de communiquer avec Telegram Bot API \cite{telegram_bot_api}.

Plutôt que d'intégrer directement les appels HTTP à l'intérieur du moteur de détection, un composant indépendant nommé \texttt{telegram\_notifier.py} est développé. Cette séparation des responsabilités permet de rendre le projet plus modulaire et facilite les évolutions futures.

Le module de notification est chargé exclusivement de transmettre les messages vers Telegram. Il ne réalise aucune opération de détection et ne possède aucune connaissance du fonctionnement interne du moteur Scapy. Cette approche respecte le principe de responsabilité unique (\textit{Single Responsibility Principle}) couramment utilisé dans le développement logiciel.

La communication avec Telegram est réalisée à l'aide de la bibliothèque Python \texttt{requests}. Cette bibliothèque simplifie l'envoi de requêtes HTTP vers Telegram Bot API tout en offrant des mécanismes de gestion des erreurs permettant d'améliorer la robustesse du système.

Le module développé expose une unique fonction publique nommée \texttt{send\_notification()}. Cette fonction reçoit le contenu du message à transmettre, construit la requête HTTP puis vérifie la réponse renvoyée par Telegram avant d'indiquer si l'envoi a été réalisé avec succès.

Cette architecture permet à n'importe quel futur composant du projet d'envoyer une notification sans avoir à connaître les détails de communication avec Telegram.

\subsection{Intégration avec le moteur de détection SSH}

Après la validation indépendante du module de notification, celui-ci est intégré au moteur de détection développé avec Scapy \cite{scapy_docs}.

L'objectif consiste à automatiser entièrement l'envoi des alertes. Désormais, aucune intervention humaine n'est nécessaire entre la détection d'une attaque et la transmission de la notification.

Le moteur de détection continue d'assurer uniquement l'observation du trafic réseau, le comptage des tentatives de connexion et l'identification des comportements suspects. Lorsqu'une adresse IP dépasse le seuil configuré dans la fenêtre temporelle glissante, le détecteur appelle simplement la fonction \texttt{send\_notification()}.

Cette approche présente plusieurs avantages. Le moteur de détection reste indépendant de Telegram, tandis que le module de notification peut évoluer sans modifier les algorithmes de détection.

Afin d'éviter la génération de notifications multiples lors d'une même attaque, le déclenchement de l'alerte est effectué uniquement lorsque le compteur atteint exactement le seuil configuré. Cette amélioration empêche l'envoi de messages répétitifs tout en garantissant qu'une seule notification est produite pour chaque nouvelle attaque détectée.

L'intégration du module est ensuite validée en générant plusieurs tentatives de connexion SSH depuis la machine Kali Linux.

Le détecteur identifie correctement les paquets TCP SYN, incrémente le compteur associé à l'adresse IP source puis déclenche automatiquement l'envoi d'une notification lorsque le seuil est atteint.

\subsection{Construction d'une alerte professionnelle}

La première version du système de notification envoyait uniquement un message générique indiquant qu'une attaque SSH avait été détectée.

Bien que cette approche permette de vérifier le bon fonctionnement de Telegram, elle ne fournit pas suffisamment d'informations pour permettre une analyse rapide de l'incident ou une automatisation des actions de réponse.

Le contenu de la notification a donc été enrichi afin de transmettre directement toutes les informations nécessaires à l'administrateur réseau.

Chaque notification contient désormais le type d'attaque détectée, le niveau de gravité, la date et l'heure de détection, les adresses IP source et destination, le port cible, le protocole utilisé, le nombre de tentatives observées ainsi que la durée de la fenêtre temporelle utilisée par le moteur de détection.

Cette structure présente également un intérêt majeur pour la suite du projet. Les informations générées par le moteur de détection pourront être directement réutilisées par le module Netmiko afin de construire automatiquement les règles ACL destinées à bloquer l'adresse IP malveillante sur le routeur Cisco.

\section{Validation du système de notification}

\subsection{Validation expérimentale}

Une série de tests a été réalisée afin de vérifier le bon fonctionnement du système de notification développé durant cette phase. Chaque fonctionnalité a été validée individuellement avant son intégration complète au moteur de détection SSH.

La première validation a consisté à vérifier la création du bot Telegram ainsi que l'obtention des paramètres nécessaires à la communication avec Telegram Bot API \cite{telegram_bot_api}. Le Bot Token et le Chat ID ont été récupérés avec succès, permettant ainsi au programme Python de communiquer avec les serveurs Telegram.

Une seconde série de tests a permis de vérifier le fonctionnement du module \texttt{telegram\_notifier.py}. Plusieurs messages de test ont été transmis afin de confirmer la capacité du module à envoyer automatiquement des notifications sans intervention de l'utilisateur.

Après cette validation indépendante, le module de notification a été intégré au moteur de détection développé avec Scapy \cite{scapy_docs}. Des scénarios simulant une attaque SSH ont ensuite été exécutés depuis la machine Kali Linux.

À chaque tentative de connexion, le détecteur capture les paquets TCP SYN, met à jour le compteur associé à l'adresse IP source puis compare le nombre de tentatives au seuil configuré.

Lorsque le seuil est atteint à l'intérieur de la fenêtre temporelle glissante, une unique notification est automatiquement générée et transmise à l'administrateur via Telegram.

Les différents essais réalisés confirment le bon fonctionnement de l'ensemble de la chaîne de traitement. Les notifications sont envoyées uniquement lorsqu'une activité réellement suspecte est détectée, évitant ainsi la génération d'alertes inutiles.

\subsection{Analyse des résultats}

Les expérimentations réalisées démontrent que l'intégration de Telegram Bot API constitue une solution simple, fiable et efficace pour assurer la notification automatique des incidents de sécurité \cite{telegram_bot_api}.

La séparation entre le moteur de détection et le module de notification améliore considérablement l'architecture logicielle du projet. Chaque composant possède désormais une responsabilité clairement définie, ce qui facilite la maintenance et limite les dépendances entre les différents modules.

Le développement d'un module Python dédié permet également de centraliser l'ensemble des communications avec Telegram. Toute évolution future du système de notification pourra ainsi être réalisée sans modifier les algorithmes de détection développés avec Scapy \cite{scapy_docs}.

L'amélioration apportée au mécanisme de déclenchement des alertes constitue également un résultat important. Le remplacement d'une condition de type \texttt{count >= THRESHOLD} par une comparaison stricte \texttt{count == THRESHOLD} permet d'éviter l'envoi de notifications multiples lors d'une même attaque tout en conservant une bonne réactivité.

L'enrichissement du contenu des notifications représente une étape essentielle dans la construction du système d'auto-défense réseau. Les informations transmises ne servent plus uniquement à informer l'administrateur, mais constituent également les données qui seront exploitées par le module de réponse automatique.

Cette conception permet de préparer naturellement l'intégration de Netmiko sans modifier l'architecture existante. Les informations relatives à l'attaque pourront être directement utilisées pour générer dynamiquement les règles de filtrage sur le routeur Cisco.

\section{Développement du mécanisme de réponse automatique}

Après la mise en place du système de notification, l'étape suivante consiste à automatiser la réponse réseau. L'objectif est de permettre au système ANSDS de communiquer automatiquement avec le routeur Cisco et d'appliquer une mesure de protection lorsqu'une adresse IP malveillante est identifiée.

\subsection{Préparation du routeur Cisco}

Avant d'automatiser les opérations de configuration, le routeur Cisco doit être préparé afin d'autoriser une connexion distante sécurisée depuis le serveur Ubuntu.

Cette préparation constitue une étape indispensable pour permettre au module Netmiko d'établir une session SSH avec le routeur et d'exécuter les commandes nécessaires à la gestion des ACL \cite{netmiko_docs,cisco_ios}.

\subsubsection{Configuration SSH du routeur}

La configuration du service SSH est réalisée sur le routeur Cisco afin d'autoriser les connexions distantes authentifiées \cite{rfc4253,cisco_ios}.

Les paramètres nécessaires sont configurés puis vérifiés avant de procéder à l'intégration avec Netmiko.

\subsubsection{Validation de la connexion SSH}

Une première connexion SSH est réalisée manuellement afin de vérifier que le routeur accepte correctement les connexions provenant du serveur Ubuntu.

Cette validation permet de distinguer les éventuels problèmes liés à la configuration réseau ou au service SSH des problèmes qui pourraient être introduits ultérieurement par Netmiko.

\subsection{Installation et configuration de Netmiko}

Netmiko est une bibliothèque Python spécialisée dans l'automatisation des équipements réseau. Elle permet notamment d'établir des connexions SSH avec des équipements Cisco et d'exécuter automatiquement des commandes de configuration \cite{netmiko_docs}.

Dans le cadre du projet ANSDS, Netmiko constitue l'interface entre le moteur logiciel développé en Python et le routeur Cisco.

\subsubsection{Installation de la bibliothèque}

La bibliothèque Netmiko est installée dans l'environnement Python utilisé pour le projet.

Une fois l'installation terminée, une vérification est effectuée afin de s'assurer que la bibliothèque peut être importée correctement par les scripts Python.

\subsubsection{Premier test de connexion}

Un premier script est développé afin de vérifier la capacité de Netmiko à établir une session SSH avec le routeur Cisco \cite{netmiko_docs}.

Cette étape permet de valider les paramètres de connexion, notamment l'adresse IP du routeur, le nom d'utilisateur, le mot de passe ainsi que le type d'équipement Cisco.

\subsubsection{Récupération automatique des informations du routeur}

Après validation de la connexion, le script est utilisé pour exécuter automatiquement des commandes de consultation sur le routeur.

Cette fonctionnalité confirme que le programme Python dispose des droits nécessaires pour interagir avec l'équipement et constitue la base de la future automatisation des ACL.

\subsection{Développement du module Cisco}

Afin de conserver une architecture modulaire, les opérations relatives au routeur Cisco sont regroupées dans un module Python indépendant nommé \texttt{cisco\_acl\_manager.py}.

\subsubsection{Architecture modulaire}

Le module Cisco est séparé du moteur de détection et du module Telegram. Cette organisation permet de conserver une séparation claire des responsabilités :

\begin{itemize}
    \item Scapy assure la capture et l'analyse du trafic \cite{scapy_docs} ;
    \item le moteur de détection identifie les comportements suspects ;
    \item Telegram assure la notification ;
    \item Netmiko assure la communication avec le routeur \cite{netmiko_docs} ;
    \item le module Cisco assure la gestion des ACL \cite{cisco_ios}.
\end{itemize}

Cette architecture facilite la maintenance du système et permet de faire évoluer chaque composant indépendamment.

\subsubsection{Création dynamique d'une ACL}

Lorsqu'une adresse IP malveillante est identifiée, le module Cisco peut générer dynamiquement une règle \texttt{ACL} correspondant à cette adresse \cite{cisco_ios}.

L'adresse IP détectée par le moteur de sécurité est transmise au module Cisco, qui construit ensuite la commande nécessaire à l'application de la règle sur le routeur.

Cette approche permet d'éviter la configuration manuelle des adresses bloquées et constitue le principe central de la réponse automatique du système.

\subsubsection{Suppression automatique d'une ACL}

Le mécanisme de blocage est conçu pour être temporaire. Après expiration de la durée configurée, le module Cisco supprime automatiquement la règle précédemment créée.

Cette fonctionnalité évite qu'une ACL temporaire reste active indéfiniment et permet au réseau de revenir automatiquement à son état initial.

\subsection{Gestion des exceptions}

L'automatisation d'un équipement réseau nécessite également une gestion appropriée des erreurs susceptibles de survenir lors de la communication.

\subsubsection{Gestion des erreurs de communication}

Les erreurs de connexion, les problèmes d'authentification ou les indisponibilités temporaires du routeur peuvent empêcher l'exécution correcte d'une commande.

Le module Cisco doit donc intercepter ces exceptions afin d'éviter l'arrêt brutal du programme principal.

\subsubsection{Utilisation des blocs \texttt{try}, \texttt{except} et \texttt{finally}}

Les blocs \texttt{try}, \texttt{except} et \texttt{finally} permettent de séparer l'exécution normale du traitement des erreurs et des opérations devant être réalisées systématiquement lors de la fermeture de la connexion.

Cette organisation améliore la robustesse du système et garantit que les ressources utilisées lors de la communication avec le routeur sont correctement libérées.

\subsubsection{Validation du mécanisme de gestion des exceptions}

Des tests sont réalisés afin de vérifier le comportement du module en cas d'erreur de communication avec le routeur.

La validation confirme que les exceptions sont correctement interceptées et que le moteur principal peut continuer son fonctionnement sans interruption imprévue.

\subsection{Intégration avec le moteur de détection}

Après validation indépendante du module Cisco, celui-ci est intégré au moteur de détection.

\subsubsection{Transmission de l'adresse IP détectée}

Lorsqu'un comportement suspect est confirmé, l'adresse IP source identifiée par le moteur de détection est transmise au module Cisco.

Cette information constitue l'élément principal utilisé pour construire dynamiquement la règle ACL de blocage.

\subsubsection{Enchaînement automatique des modules}

L'intégration permet désormais d'obtenir une première chaîne automatisée :

\begin{center}
\textbf{Détection SSH $\rightarrow$ Alerte Telegram $\rightarrow$ Netmiko $\rightarrow$ ACL Cisco}
\end{center}

Le moteur de détection identifie l'événement, Telegram informe l'administrateur et Netmiko applique automatiquement la mesure de protection sur le routeur Cisco.

\subsubsection{Architecture finale du système}

À l'issue de cette phase, les différents composants développés sont interconnectés tout en conservant leur séparation fonctionnelle.

Le moteur de détection est chargé de l'analyse du trafic, le module Telegram assure la notification et le module Cisco réalise la réponse réseau.

Cette architecture constitue la base de l'évolution future vers une détection multi-indicateurs et une réponse automatisée plus avancée.

\subsection{Validation expérimentale}

Une série de tests est réalisée afin de valider progressivement l'ensemble du mécanisme de réponse automatique.

Les validations portent notamment sur :

\begin{itemize}
    \item la connexion SSH au routeur Cisco ;
    \item l'installation et le fonctionnement de Netmiko ;
    \item l'exécution automatique de commandes ;
    \item la création dynamique d'une ACL ;
    \item le blocage de l'adresse IP détectée ;
    \item la suppression automatique de l'ACL ;
    \item la gestion des erreurs de communication ;
    \item l'intégration avec le moteur de détection ;
    \item l'enchaînement entre la détection, la notification et la réponse.
\end{itemize}

Les différents essais permettent de vérifier que l'adresse IP détectée peut être transmise automatiquement au module Cisco et utilisée pour appliquer la règle de blocage correspondante.

\section{Analyse des résultats}

Les expérimentations réalisées montrent que l'intégration de Telegram et de Netmiko permet de transformer progressivement le moteur de détection en un système capable non seulement d'identifier une activité suspecte, mais également d'engager une réponse automatisée.

La séparation des responsabilités entre les différents modules constitue un résultat important de cette phase. Le moteur de détection reste consacré à l'analyse du trafic, tandis que les modules Telegram et Cisco assurent respectivement la notification et la réponse réseau.

L'utilisation de Netmiko permet également de supprimer la nécessité d'intervenir manuellement sur le routeur Cisco après chaque détection. L'adresse IP identifiée par le moteur peut être transmise directement au module Cisco afin de générer la règle de filtrage correspondante.

La suppression automatique de l'ACL constitue également une fonctionnalité importante. Le blocage n'est pas permanent et le réseau peut revenir automatiquement à son état initial après expiration de la durée configurée.

La chaîne de traitement obtenue à l'issue de cette phase peut ainsi être résumée comme suit :

\begin{center}
\textbf{Détection $\rightarrow$ Notification $\rightarrow$ Réponse automatique $\rightarrow$ Blocage temporaire $\rightarrow$ Suppression de l'ACL}
\end{center}

Cette architecture prépare également l'évolution du système vers une détection multi-indicateurs, qui sera développée dans la phase suivante.

\section{Conclusion}

Cette phase a permis de faire évoluer le système ANSDS d'un moteur de détection capable d'identifier des tentatives SSH vers une architecture intégrant les premiers mécanismes de notification et de réponse automatique.

Le système est désormais capable de détecter un comportement suspect, d'informer automatiquement l'administrateur via Telegram et d'interagir avec un routeur Cisco à l'aide de Netmiko.

L'intégration du module Cisco permet d'appliquer dynamiquement une ACL destinée à bloquer l'adresse IP identifiée. Le caractère temporaire du blocage ainsi que la suppression automatique de l'ACL permettent de compléter le cycle de protection sans intervention manuelle.

La séparation des responsabilités entre Scapy, le moteur de détection, Telegram, Netmiko et le module de gestion Cisco fournit une architecture modulaire et évolutive.

Cette phase constitue ainsi une étape essentielle vers l'objectif final d'un système d'auto-défense réseau capable de détecter plusieurs catégories de comportements malveillants, de corréler les événements et d'appliquer automatiquement une réponse adaptée.
